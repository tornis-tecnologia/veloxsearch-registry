# veloxsearch-registry

The integration registry for
[VeloxSearch](https://github.com/tornis-tecnologia/veloxsearch-oss).

An integration turns a log or metric source into a working view: what to
collect and how (Fluent Bit inputs, parsers, filters and processors with the
parameters an operator may set), how OpenSearch stores it (index templates,
ingest pipelines, lifecycle) and what to look at (dashboards). It is **data,
not code**: the control plane applies it with a fixed engine, every package
is ed25519-signed and verified before a byte reaches a cluster, and nothing
in a package can execute code on a host.

Contributing an integration needs no Rust.

## Two formats, two consumers

| | `integrations/` + `catalog.json` — **Spec 1.x** | `packages/` + `packages/index.json` — **Spec 2.0** |
| --- | --- | --- |
| Consumer | the in-cluster DaemonSet installed by the core | **Velox Mesh** policies applied by **Velox Agent** on hosts |
| What a package carries | one fixed Fluent Bit template, pipeline, index template, dashboards | **streams** the operator turns on and configures: a Fluent Bit input with typed fields, parsers, a processor chain, backend settings, lifecycle, dashboards |
| Configuration format | classic, text interpolation (8 tokens) | YAML (Fluent Bit ≥ 3.2), built as an object by the Mesh |
| Versions | one per id | several, immutable, with compatibility minimums |
| Artifact names | `veloxagent-<id>-<signal>-v<major>` | `veloxagent-<stream>.<id>-v<major>` |
| Docs | [core `docs/integrations/`](https://github.com/tornis-tecnologia/veloxsearch-oss/tree/main/docs/integrations) | [`docs/spec/README.md`](docs/spec/README.md), [`docs/PACKAGING.md`](docs/PACKAGING.md), [`docs/mesh-integration-guide.md`](docs/mesh-integration-guide.md) |

The 1.x tree is a byte-equivalent extraction of the recipes compiled into the
core and is held that way by the core's golden gates; it is regenerated, not
edited. The 2.0 tree is where new work happens.

## Layout

```
catalog.json                 Spec 1.x catalogue (cluster path)
integrations/<id>/           Spec 1.x packages — generated from the core's recipes
packages/
  index.json                 Spec 2.0 catalogue — generated by scripts/build_index.py
  <id>/<version>/            one immutable package version (manifest, streams/, dashboards/, docs/)
fluent-bit/<docs-version>/   catalogue of allow-listed Fluent Bit plugins and their parameters
schemas/                     JSON Schemas of Spec 2.0
docs/spec/                   the Spec 2.0 text, rules R1..R24, a conformance example
docs/PACKAGING.md            how to write a package
docs/mesh-integration-guide.md  what the Mesh, console, core and agent implement
scripts/                     validators, index builder, reference compiler, test runners
keys/                        the public half of the signing key (also compiled into the core)
tests/activations/<id>/      activation fixtures CI dry-runs through Fluent Bit
```

## Spec 2.0 packages available

Generated into [`packages/index.json`](packages/index.json). See each
package's `docs/README.<lang>.md`.

## Tooling

```sh
pip install pyyaml jsonschema referencing

scripts/check_spec.py                  # schemas valid, example conforms, bad variants rejected
scripts/check_catalog.py               # Fluent Bit plugin catalogue
scripts/validate_v2.py [--examples]    # every packages/<id>/<version>: schemas + R1..R23
scripts/build_index.py [--check]       # packages/index.json
scripts/render.py packages/<id>/<v> [--activation a.json] [--backend]
                                       # reference compiler: what the Mesh sends to an agent /
                                       # what the core installs in OpenSearch
FB_VERSIONS="3.2 latest" scripts/dryrun.sh          # fluent-bit --dry-run of every package (Docker)
OPENSEARCH_URL=http://localhost:9200 scripts/pipeline_test.py   # ingest pipelines vs expected (R24)
scripts/validate.py [--expect-signed]  # Spec 1.x tree
```

CI runs all of it, plus the core's golden gates against the 1.x tree and the
signature verification of every package with the `velox` binary.

## Using this registry

Nothing to configure — it is the default. To point an install at a mirror or
at a local checkout:

```yaml
# in the veloxsearch-env ConfigMap
VELOX_REGISTRY_URL: "https://raw.githubusercontent.com/tornis-tecnologia/veloxsearch-registry/main"
```

```sh
# air-gapped: a local checkout, verified identically
VELOX_REGISTRY_URL=file:///srv/veloxsearch-registry
```

Signature verification is the same on every route: the trusted key is
compiled into the binary, so it works with no network and cannot be
redirected by a compromised registry. A registry that cannot be reached is a
degraded state, not a crash — the last cached catalogue is served, marked
stale.
